# 学習結果の分析

`docker/README.md` の手順で `outputs/kitti-360/large_rotation/eval/` に出力されたファイルを、どれをどの順に見れば「TLC-Calib が何をどれだけうまくやったか」が分かるかを整理する。結論から言うと、見るべき値はごく少数で、最初の1ファイルだけでこの手法の核心的な成果がほぼ判断できる。

この分析は KITTI-360 の `large_rotation` シーンに対する1回の学習結果（`train.py ... --eval --from_lidar --use_rig --opt_pose --pose_scheduler --adaptive_voxel`）を対象にしている。

## まず結論

この実行で TLC-Calib は、LiDAR-カメラ間の外部パラメータを**回転誤差 約0.11度・並進誤差 約0.11m** で復元した。論文がキャリブレーション成功の基準としている「回転誤差1度以内・並進誤差20cm以内」を、回転で約1桁、並進で約2倍の余裕をもって満たしている。しかも初期姿勢に大きな回転ずれを与えた `large_rotation` 設定でこれを達成しており、チェッカーボードなどの専用ターゲットを一切使っていない。これがこの出力から読み取れる「凄さ」である。

## 出力ファイルの全体像

```text
eval/
├── outputs.log                       # 最終評価の数値（最初に見るファイル）
├── cams_to_lidar_gt.txt              # 外部パラメータの正解値（4台のカメラ）
├── config.yml                        # この学習の設定
├── train_info.json                   # 学習時間・点数・メモリ
├── cameras.json                      # カメラ内部パラメータ・画像情報
├── input.ply                         # 初期のLiDAR点群（最適化前）
└── point_cloud/iteration_30000/
    ├── cams_to_lidar.txt             # 外部パラメータの推定値（← 正解と比較する）
    ├── pred_poses.txt                # 推定したカメラ走行軌跡（156行）
    ├── gt_poses.txt                  # 軌跡の正解値（156行）
    ├── point_cloud.ply               # 最適化後のアンカーガウシアン
    ├── offset.ply                    # 補助ガウシアン（オフセット表現）
    └── {color,opacity,cov}_mlp.pt    # 色・不透明度・形状を予測するMLPの重み
```

## 1. outputs.log

最初に開くべきファイル。学習の最終反復（30000回目）での評価結果がそのまま書かれている。注目するのは次の3行。

```text
[ITER 30000] Evaluating test:  Photo 0.040505 PSNR 22.459946, Rot_Err: 0.107243[deg], Trans_Err: 0.107389[m]
[ITER 30000] Evaluating train: Photo 0.034866 PSNR 23.468560, Rot_Err: 0.107873[deg], Trans_Err: 0.107315[m]
```

各値の意味は次のとおり。

| 値 | 意味 | 良し悪し | 今回の値 |
| --- | --- | --- | --- |
| `Rot_Err [deg]` | 回転キャリブレーション誤差 | 小さいほど良い | 0.107度（test） |
| `Trans_Err [m]` | 並進キャリブレーション誤差 | 小さいほど良い | 0.107m（test） |
| `PSNR [dB]` | 画像再構成品質 | 大きいほど良い | 22.46（test）/ 23.47（train） |
| `Photo` | フォトメトリック損失 | 小さいほど良い | 0.0405（test） |

ここで最も重要なのは `Rot_Err` と `Trans_Err` である。これは推定した外部パラメータ $R$、$t$ が正解からどれだけずれているかを直接測った値で、TLC-Calib が解こうとしている問題そのものの答え合わせになっている。

**なぜこの2つの数値で凄さが分かるのか。** 論文はキャリブレーションの成否を「回転誤差1度以内・並進誤差20cm以内」と定義し、これを満たした割合を成功率(SR)と呼んでいる。今回の値はこの基準を大きく下回る。

| 指標 | 成功基準 | 今回の値 | 余裕 |
| --- | --- | --- | --- |
| 回転誤差 | ≤ 1.0 度 | 0.107 度 | 約9倍の余裕 |
| 並進誤差 | ≤ 0.20 m | 0.107 m | 約2倍の余裕 |

つまりこの1シーンは「成功」どころか、基準に対してかなりの余裕をもって合格している。論文が全評価シーンで SR 100%・平均回転誤差 約0.1度を報告しているのと整合する結果が、手元の1回の学習で再現できていることになる。

`test` と `train` でほぼ同じ誤差になっている点も見ておきたい。学習に使った視点と使っていない視点で精度が変わらないということは、特定の画像に過剰適合したのではなく、シーン全体に対して一貫した姿勢を推定できていることを意味する。

ログには各カメラ個別の誤差も出ている。

```text
[CAM 0] Rot_Err: 0.104[deg], Trans_Err: 0.108[m]
[CAM 1] Rot_Err: 0.072[deg], Trans_Err: 0.112[m]
[CAM 2] Rot_Err: 0.159[deg], Trans_Err: 0.094[m]
[CAM 3] Rot_Err: 0.093[deg], Trans_Err: 0.115[m]
```

4台すべてが回転0.16度以内・並進0.12m以内に収まっている。`--use_rig` で4台の姿勢をまとめて最適化しているため、特定のカメラだけが極端に外れることなく全カメラが揃って高精度になっている。

## 2. cams_to_lidar_gt.txt と cams_to_lidar.txt

ログの数値が「どこから来た誤差なのか」を自分の目で確かめられるのがこの2ファイル。前者が外部パラメータの正解値、後者が30000反復後の推定値で、どちらも同じ形式で4台ぶんのカメラ姿勢が並ぶ。

各行の形式は次のとおり。

```text
カメラ番号  r00 r01 r02 tx  r10 r11 r12 ty  r20 r21 r22 tz  0 0 0 1
```

先頭のカメラ番号に続く16個の数値が、LiDAR座標系からカメラ座標系への 4×4 同次変換行列を行優先で並べたものになっている。左上 3×3 が回転 $R$、4列目の `tx, ty, tz` が並進 $t$ である。

並進 $t$ は読み取りやすいので、ここを比べると誤差の出どころが直感的に分かる。カメラ0の並進列だけ取り出すと次のようになる。

| | tx | ty | tz |
| --- | --- | --- | --- |
| 正解 (`gt`) | 0.804 | 0.299 | −0.177 |
| 推定 (`pred`) | 0.839 | 0.246 | −0.088 |
| 差 | +0.035 | −0.054 | +0.089 |

この差ベクトルの長さ（ユークリッドノルム）は約 0.110m で、ログの `[CAM 0] Trans_Err: 0.108m` とほぼ一致する。つまりログの並進誤差は、この2ファイルの並進列を引き算した距離そのものである。次のように手元で再現できる。

```python
import math
def load(fn):
    d = {}
    for line in open(fn):
        p = line.split()
        if p:
            v = list(map(float, p[1:17]))
            d[int(p[0])] = v
    return d

gt = load("cams_to_lidar_gt.txt")
pr = load("point_cloud/iteration_30000/cams_to_lidar.txt")
for i in sorted(gt):
    tg = (gt[i][3], gt[i][7], gt[i][11])   # tx, ty, tz
    tp = (pr[i][3], pr[i][7], pr[i][11])
    err = math.sqrt(sum((a - b) ** 2 for a, b in zip(tg, tp)))
    print(f"CAM {i}: Trans_Err = {err:.3f} m")
```

回転誤差については注意が必要である。上の2つの行列の回転部分 $R$ を絶対姿勢のまま測地距離（2つの回転の間の最小回転角）で比べると、4台とも約0.3度になる。一方ログや論文が報告する回転誤差は約0.1度で、これより小さい。両者がずれるのは、どの座標基準で誤差を測るかが違うためである。リグ最適化では4台に共通する全体的な姿勢のずれと各カメラ固有のずれが分離され、論文の指標は後者（カメラ間の相対関係）を測っている。絶対姿勢同士の単純な差には全カメラ共通のオフセットぶんが上乗せされるため、わずかに大きく出る。どちらの測り方でも1度の基準は満たしているが、ログの値を正式な回転誤差として扱うのが正しい。より厳密な回転誤差が必要なら、README に書かれている `metrics_pose.py` を実行すると `rig_results.json` に評価値が出力される。

## 3. pred_poses.txt と gt_poses.txt

外部パラメータ（カメラとLiDARの取り付け関係）とは別に、走行中の各時刻のカメラ姿勢、つまり走行軌跡そのものを推定値と正解値で並べたファイル。各156行あり、行頭が `カメラ番号 フレーム番号` で、続く16個は cams_to_lidar と同じ4×4行列の形式になっている。

外部パラメータがLiDARに対するカメラの固定的な取り付け関係なのに対し、こちらはフレームごとに変化するシーン中での絶対的な動きを表す。並進列の `tx`（先頭フレームで約 −26.9）が時系列に沿って変化していくのが見て取れ、車両が前進していく軌跡に対応する。推定軌跡が正解軌跡をよく追えていれば、姿勢最適化が時間方向にも安定して働いたことの裏づけになる。キャリブレーション精度そのものは outputs.log と cams_to_lidar.txt で判断できるので、このファイルは補助的な確認材料と考えてよい。

## 4. train_info.json

手法の効率と規模を見るファイル。

```json
{
    "Initial point number": 2752123,
    "Point number at iteration 30000": 369820,
    "peak_memory": "7.12 GB",
    "avg_memory": "5.37 GB",
    "train_time": "0:14:12"
}
```

読みどころは2つある。1つは点数の変化で、初期の約275万点のLiDAR点群が、最終的に約37万個のアンカーガウシアンへと約1/7に圧縮されている。これは適応的密度制御（`--adaptive_voxel`）が効き、シーンの表現に本当に必要な場所へガウシアンを集約した結果である。もう1つは計算コストで、約14分・ピークメモリ 7.12GB という、1枚のGPUで現実的に回せる規模で上記の精度に到達している。専用ターゲットの設置や撮影が要らないことと合わせて、現場での再キャリブレーションに使える実用性を示している。

## 5. PSNR と ply ファイル（新視点合成の品質）

`Rot_Err`/`Trans_Err` が姿勢の直接的な答え合わせだとすると、もう一つ別の角度からの検証が新視点合成(NVS)の品質、すなわち PSNR である。外部パラメータがずれていると複数視点の画像が幾何的に噛み合わず、再構成画像はぼやけたり破綻したりする。逆に PSNR が高いということは、姿勢が合っていて画像再構成に一貫性があることを別の観点から裏づける。今回は test で 22.46dB が出ており、姿勢誤差の小ささと整合する。

実際の見た目を確認したい場合は ply ファイルを 3D ビューア（オンラインの 3DGS ビューアや CloudCompare など）で開く。

- `input.ply`: 最適化前の初期LiDAR点群。出発点の3D構造。
- `point_cloud/iteration_30000/point_cloud.ply`: 最適化後のアンカーガウシアン。LiDAR由来の足場。
- `point_cloud/iteration_30000/offset.ply`: 補助ガウシアン。LiDARが観測していない空や建物上部まで含めてシーンを埋めている部分にあたる。

`{color,opacity,cov}_mlp.pt` は、各ガウシアンの特徴ベクトルと視線方向から色・不透明度・形状を予測する小さなニューラルネット（MLP）の重みで、レンダリングや再学習に使う。数値を直接読むものではない。

## 6. config.yml

最後に、上記の結果がどういう条件で得られたかを確認するファイル。今回の凄さを正しく評価するうえで重要な設定は次のとおり。

| 設定 | 値 | 意味 |
| --- | --- | --- |
| `dataset` | kitti-360 | 評価データセット |
| `from_lidar` | true | LiDAR点群をアンカーの足場として使用 |
| `use_rig` | true | 4台のカメラ姿勢をまとめてリグ最適化 |
| `opt_pose` | true | カメラ姿勢（外部パラメータ）も最適化対象 |
| `adaptive_voxel` | true | 適応的なボクセル分割でガウシアンを配置 |
| `iterations` | 30000 | 最適化反復数 |

`opt_pose: true` は、外部パラメータを固定せず最適化で求めていることを示す。つまり前掲の 0.1度台の誤差は、与えられた姿勢を使い回した結果ではなく、ずれた初期姿勢から最適化で正しい値に到達した結果である。`large_rotation` という初期回転ずれの大きい設定でこれが成り立っていることが、この手法のロバスト性を端的に表している。

## まとめ

| 見るファイル | 注目する値 | 分かること |
| --- | --- | --- |
| `outputs.log` | `Rot_Err` / `Trans_Err` | 外部パラメータの最終精度（核心の成果） |
| `outputs.log` | `test` と `train` の比較 | 過剰適合せず一貫した姿勢を推定できたか |
| `cams_to_lidar_gt.txt` ↔ `cams_to_lidar.txt` | 並進列 `tx,ty,tz` の差 | ログの誤差を自分で再現・実感する |
| `pred_poses.txt` ↔ `gt_poses.txt` | 各フレームの並進列 | 走行軌跡を時間方向に追えているか（補助確認） |
| `train_info.json` | 点数・時間・メモリ | 約275万→37万点・14分・7GB の効率 |
| `PSNR` と `*.ply` | 22.46dB・3D表現 | 別観点(NVS)からの姿勢一貫性の裏づけ |
| `config.yml` | `opt_pose` / `use_rig` / `large_rotation` | どれだけ厳しい条件で達成したか |

最短ルートは、`outputs.log` の `Rot_Err`/`Trans_Err` を「1度・20cm」基準と比べることである。この1点だけで、TLC-Calib が専用ターゲットなしに、初期姿勢が大きくずれた条件から、基準を大幅に上回る精度で外部パラメータを復元できたことが分かる。
